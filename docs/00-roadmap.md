# 00 路线图：12 周，从用户态跑到内核里

目标不是「看过一遍内核书」，而是建立一条可信的因果链：用户态的一个动作 → 内核里的哪几个函数 → 数据结构怎么变 → 用什么工具能看到。

时间按每周 8-10 小时估。做不完就延长，不要压缩阶段二和三，那才是分水岭。

## 阶段一：四条线跑通（第 1-4 周）

每周一条线，顺序不要变：syscall 是后面三条线的共同入口。

| 周 | 主题 | 代码 | 必须能回答的问题 |
| --- | --- | --- | --- |
| 1 | 系统调用 | `labs/01_syscall` | 一次 write 从 libc 到磁盘经过哪些函数？vDSO 为什么不用进内核？ |
| 2 | 进程 | `labs/02_process` | fork 复制了什么、没复制什么？僵尸进程为什么不能被自动回收？exec 后 pid 为什么不变？ |
| 3 | 内存 | `labs/03_memory` | malloc 什么时候走 brk、什么时候走 mmap？缺页时内核具体分配了什么？ |
| 4 | 文件 | `labs/04_file` | write 返回到落盘之间发生了什么？路径解析的缓存层次是什么？ |

每周验收（缺一不算完成）：

1. 程序跑出数字，记录在 `docs/notes/weekN.md`（自己建目录）。
2. 用 gdb 或源码把数字对应的函数找到，截图或粘贴关键代码片段。
3. 写 300 字以内的小结：这个动作在内核里最贵的部分是什么，为什么。

## 阶段二：观测手段（第 5-6 周）

| 周 | 内容 | 产出 |
| --- | --- | --- |
| 5 | `docs/01-observation.md` 全部工具过一遍：mini_strace、/proc、ftrace、perf、bpftrace | 给每个实验补一条「用 A 工具看比用 printf 看多知道了什么」 |
| 6 | 把阶段一的四个实验用 ftrace 重看一遍，尤其是 `do_sys_openat2`、`handle_mm_fault`、`filemap_fault` | 一份 ftrace function_graph 输出，标出耗时最长的三层调用 |

这一阶段的核心是换视角：从「打印结果」换成「看调用链和耗时」。从这里开始，你不再依赖猜测。

## 阶段三：调度子系统深入（第 7-10 周）

选调度的理由：它同时牵扯进程、内存（栈和 mm）、中断、时钟、同步，是性价比最高的深挖对象。内存管理也可以，路线在 `docs/04-memory.md` 末尾给了替代方案。

| 周 | 内容 | 验收 |
| --- | --- | --- |
| 7 | 读 `docs/07-sched-deepdive.md`，对照 6.x 源码看 `fair.c` 的 `update_curr`、`check_preempt_tick`、`pick_next_task_fair` | 画出 task_struct → sched_entity → cfs_rq → rq 的指针图，标注每个字段的来源 |
| 8 | 跑 `labs/06_sched` 两个实验，再用 `/proc/sched_debug`、`/proc/<pid>/sched`、`/proc/schedstat` 交叉验证 | 用三处数据解释同一个现象（例如 nice 10 的任务为什么拿 7.4%） |
| 9 | 搭 QEMU + gdb（`docs/06-qemu-gdb.md`），断在 `__schedule`，跟一次完整切换 | 说清 prev/next 是谁、为什么切、`switch_to` 前后发生了什么 |
| 10 | 改内核：加 printk、改一个调度参数、加一个 tracepoint，重新编译进 QEMU 验证 | 改动前后的数据对比，以及你对「这个参数影响谁」的解释 |

阶段三的判定标准只有一条：能在 gdb 里单步走完一次 `__schedule → context_switch → switch_to`，并说出每一步改了哪个寄存器或哪个字段。

## 阶段四：收口（第 11-12 周）

- 挑一个真实问题做闭环，例如「容器里 Java 进程 RSS 很高但堆不大」：从 `/proc/<pid>/smaps_rollup`、page cache、匿名页、THP 一路查到内核路径。
- 把 12 周的笔记压成一页「因果链」：动作 → 系统调用 → 内核函数 → 数据结构 → 观测命令。
- 复盘：哪些结论是实测的，哪些只是从书里抄的。抄的部分标出来，下一轮补实验。

## Java 经验怎么迁移

| Java 里熟悉的 | 内核里对应的 | 差异点 |
| --- | --- | --- |
| JVM 堆、`-Xmx` | 匿名 VMA + 缺页 | JVM 预申请虚拟地址，物理页仍是按需分配 |
| `FileChannel.force()` | `fsync` / `fdatasync` | 都要等日志提交，成本量级相同 |
| `MappedByteBuffer` | `mmap` | Java 的 force 对应 msync，但 JVM 不保证立即刷 |
| 线程池线程 | `clone` + `task_struct` | 内核不区分进程和线程，只看共享了哪些资源 |
| `jstack` 看线程状态 | `/proc/<pid>/task/*/stat`、`/proc/<pid>/sched` | 内核状态只有 R/S/D/Z，Java 的 BLOCKED/WAITING 是 JVM 自己维护的 |
| GC 停顿 | 调度延迟 / 内存回收 | 一个是应用层暂停，一个是内核让出 CPU，别混为一谈 |

## 每周固定动作

1. 先写「我猜会怎样」，再跑。
2. 跑完把差异写下来，尤其是猜错的地方。
3. 打开源码找那三行关键代码，贴进笔记。
4. 结尾问自己：这个结论能不能用一条命令在另一台机器上复现。

## 不要做的事

- 不要一上来读 `kernel/sched/core.c` 全文。先带着「这次切换是谁触发的」这种具体问题进去。
- 不要用「背函数名」代替跑实验。函数名会随版本变，路径不会。
- 不要在宿主机上改内核、装自定义模块。所有内核侧实验都在 QEMU 里做。
- 不要同时开三条深挖线。调度和内存选一个，另一个只做用户态观察。
